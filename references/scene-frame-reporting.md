# 장면 프레임형 독자 경험 가이드

이 문서는 검증된 실제 사례 하나를 규범으로 일반화한다. 원형은
2026-08-28에 발행된 온보딩 사이트의 「아키텍처 그림, 문서 쉽게 만들기 — C4 · ADR · arc42」
초보자 장면 프레임 리포트다. 이 리포트는 유튜브 원본을 자막 근거와 7개 캡처 프레임으로
나눠, 어려운 문서화 방법론을 초보자 눈높이로 통과시켰다. 여기서 배울 것은 유튜브 요약이
아니라 **근거와 설명을 한 화면에 붙여 놓는 독자 경험 구조**다.

C4 보고서로 치환하면 대응은 다음과 같다.

```text
장면(scene)     = 독자의 이해 경로를 이루는 단계(질문·View·흐름)
프레임(frame)   = 그 단계에서 근거로 보여주는 것: 다이어그램, 원문 인용, 스냅샷
증거 체인       = 소스 → Claim → 결론의 연결
```

## 언제 쓰는가

- 초보자용 보고서는 이 구조를 **기본으로 제안**한다.
- 전문가용 보고서는 전체 구조는 자유지만, 증거 체인 종합과 검증 로그 공개는 공통으로 권장한다.
- 자료가 아주 작으면 섹션을 줄여도 된다. 줄이는 것과 숨기는 것은 다르다.

## 8개 요소와 최소 계약

### 1. 한눈 요약 — 30초 만에 이해하기

- 최소 계약: 첫 화면에서 본문을 읽지 않고도 시스템이 무엇을 하고 어디가 핵심인지 알려야 한다.
  3~6문장. 결론이 먼저고 근거 요약이 뒤 따른다.
- 이해 경로(View 확대 순서)를 한 줄로 예고한다: "Context → Container → 주문 흐름 순으로 봅니다."
- 안티패턴: 목차만 나열한 요약, 결론 없는 "이 문서에서는 ~을 다룹니다".

### 2. 독자 계약 — 증거를 읽는 법

- 최소 계약: 이 보고서의 사실 표기 체계(`[확인됨]`, `[분류됨]`, `[제한적 추론]`, `[확인 필요]`,
  `[충돌]`)를 독자에게 먼저 가르친다. 각 표기가 무엇을 보증하고 무엇을 보증하지 않는지
  한 줄씩 설명한다.
- 근거 종류가 여럿이면 구분해 이름 붙인다. 원형 사례는 "자막 근거 vs 프레임 근거"를
  나눠 보여줬다. C4 보고서라면 "설계 문서 근거 vs 코드 근거 vs 배포 설정 근거"가 대응된다.
- 안티패턴: 표기를 설명 없이 본문에 뿌리기, 근거 위치를 독자가 추측하게 만들기.

### 3. 장면 목차 — 클릭하면 프레임으로 이동

- 최소 계약: 이해 경로의 각 장면을 목차로 나열하고, 각 항목이 해당 섹션·프레임으로
  이동해야 한다(HTML이라면 문서 내 앵커 점프).
- 목차 항목은 내부 ID가 아니라 독자 언어의 질문·주제로 쓴다.
  "3. 실제 요청 하나를 따라가 보기 — Dynamic"처럼 번호 + 질문 + View 이름.
- 깨진 앵커는 기능 부패다. validator가 HTML-STATIC-006으로 잡는다.

### 4. 장면 카드 — 프레임과 설명을 나란히

- 최소 계약: 각 장면에서 설명과 근거 프레임이 같은 화면에 함께 보인다.
  프레임은 다이어그램, 원문 인용(locator 포함), 구성 파일 발췌 등이다.
- 카드 순서는 모델의 이해 경로를 따른다. 카드 순서 재배치는 표현 변경이지
  canonical 사실 변경이 아니다. canonical ID 연결은 유지한다.
- 안티패턴: 근거를 전부 문서 끝에 몰아놓고 본문은 주장만 반복하기.
  독자는 주장과 근거의 거리가 멀수록 불신한다.

### 5. 증거 체인 종합 — 소스 → 결론

- 최소 계약: "어떤 소스가 어떤 결론을 지지하는가"를 한 화면의 표로 요약한다.
  행 = 주요 결론, 열 = 소스 ID·종류·locator·confidence.
- 이 표는 evidence-ledger의 요약 뷰다. ledger에 없는 결론을 표에 새로 만들면 안 된다.
- 안티패턴: 근거가 약한 결론을 표에서 빼먹기. 약한 결론일수록 표에 있어야 한다.

### 6. 그래서 무엇을 해야 할까 — 상황별 시나리오

- 최소 계약: 독자 유형·상황별로 다음 행동을 매핑한다. 예: "처음 팀에 합류했다 →
  Container View와 주문 Dynamic부터", "레거시를 인수했다 → 배포 근거와 Coverage의
  확인 필요 항목부터".
- 시나리오는 근거와 Coverage에 기반해야 한다. 근거 없는 조언은 이 섹션에도 넣지 않는다.
- 전문가용에서는 trade-off와 다음 결정 후보로 대체할 수 있다.

### 7. 검증 로그 공개 — 프레임 수·순서가 계획과 일치하는가

- 최소 계약: 기계 검증 결과를 사람 언어로 본문에서 열람 가능하게 한다.
  원형 사례는 "프레임 수·순서가 계획과 일치하는가"를 표로 공개했다.
  C4 보고서는 "View 수·step 순서·참조 무결성·validator 결과"가 대응된다.
- 본문 요약과 `qa/` 산출물이 서로 다른 말을 하면 안 된다. 본문은 qa/의 요약이다.
- 안티패턴: "검증을 통과했습니다" 한 줄만 쓰고 근거 로그는 숨기기.

### 8. 한계와 불확실성 — 숨기지 않는다

- 최소 계약: 확인하지 못한 것, 이 보고서가 답하지 못한 질문, 자료의 나이와 한계를
  독자 언어로 명시한다. Coverage의 `unknownRelevant`와 `PASS_BOUNDED`가 이 섹션의 원료다.
- 이 섹션이 없는 초보자용 보고서는 완성본이 아니다.

## 자산 무결성 — 프레임이 깨지면 보고서도 깨진 것이다

원형 사례의 실제 사고: 배포본 HTML이 존재하지 않는 `frames/scene-XX.jpg`를 참조해
장면 이미지 7장이 전부 404가 됐고, 기존 QA는 "이미지가 없는 것은 실패가 아니다" 규칙
때문에 통과했다.

규칙:

- **참조가 전혀 없는 보고서는 통과다. 참조하는데 대상이 없으면 실패다.**
- HTML이 참조하는 로컬 파일과 문서 내 앵커는 `validate_html_assets.py`의
  HTML-STATIC-005/006 검사를 통과해야 한다.
- 프레임 이미지를 쓰면 manifest에 포함하고, 브라우저 QA에서 실제로 렌더링되는지 확인한다.
  파일 존재 검사는 "그림이 완성됐다"의 증거가 아니다.
